================================================================================
BUSLY - COMPLETE PROJECT DETAILS
School Transport Management System (live GPS tracking + attendance + fleet)
================================================================================

--------------------------------------------------------------------------------
1. PROJECT OVERVIEW
--------------------------------------------------------------------------------
Busly is a school transport management platform. It tracks school buses live
on GPS, manages drivers, vehicles, routes, stops and students, records trip
attendance, generates reports, and raises alerts (e.g. geofence entry/exit).

Parts of the system:
  - Backend   : 8 FastAPI microservices + 1 API gateway + Celery workers
                (Python 3.11, Docker Compose, 12 containers total)
  - Admin     : Next.js 14 web dashboard (TypeScript + Tailwind CSS)
  - Mobile    : One Expo SDK 57 app (React Native) that reshapes itself by role
                (driver / parent / teacher / admin)
  - Data      : PostgreSQL 15 + PostGIS, Redis 7, RabbitMQ 3

Total cost to run: $0 (self-hosted with Docker + free Cloudflare Tunnel).

3. SYSTEM ARCHITECTURE
--------------------------------------------------------------------------------
  Phone (Expo Go) --\
                     +--> gateway :8000 --> auth :8001 | fleet :8002
  Laptop admin  ----/                        routing :8003 | students :8004
                                                 geo :8005 | tenant :8006
                                          notifications :8008 | celery worker
                                                |
                       postgres+postgis . redis . rabbitmq

Only port 8000 is public. Internal service ports (8001+) are NOT published.
Host port mapping avoids clashes: Postgres 5433:5432, Redis 6380:6379.

4. SERVICES AND RESPONSIBILITIES
--------------------------------------------------------------------------------
  gateway       :8000  Single public entry. Verifies RS256 JWT, enforces role
                       scopes per endpoint, enforces tenant-from-token, applies
                       login/register rate limits, proxies to microservices.
  auth          :8001  Register/login/refresh/logout, user CRUD, bcrypt
                       passwords, RS256 tokens, refresh-token revocation.
                       First-ever user of a fresh tenant becomes admin.
  fleet         :8002  Vehicles, drivers, maintenance records, report files.
  routing       :8003  Routes, stops, trips (start/complete), TSP optimizer.
  students      :8004  Students, attendance marking, ridership records.
  geo           :8005  GPS ingestion, live positions, geofence enter/exit
                       alerts, websocket streams.
  tenant        :8006  Tenant provisioning (CREATE DATABASE per school),
                       tenant registry kept in Redis.
  notifications :8008  In-app alerts feed (bell icon in admin dashboard).
  celery-worker :      Background jobs via RabbitMQ: nearest-neighbor TSP
                       route optimization, CSV report generation.
  postgres      :5433  System DB "busly" + one database per tenant
                       (e.g. tenant_default with schema "busly"). PostGIS on.
  redis         :6380  Rate-limit counters, revoked refresh tokens,
                       geofence transition state, tenant registry.
  rabbitmq      :5672  Celery broker. Management UI on :15672.
  cloudflared   :      (optional profile) Publishes gateway on a public
                       https://<random>.trycloudflare.com URL.

6. ROLES AND PERMISSIONS (enforced at the gateway, not just the UI)
--------------------------------------------------------------------------------
  Role      Mobile tabs                              Gateway scopes
  --------  ---------------------------------------  --------------------------
  driver    Home, Attendance, Vehicle, Profile       trips, vehicles, students,
                                                     attendance, gps
  parent    Tracking, Children, Profile              tracking, students,
                                                     attendance, gps (read)
  teacher   Roster, Tracking, Attendance, Profile    students, attendance,
                                                     tracking
  admin     Home, Tracking, Roster, Attendance,      everything
            Vehicle, Profile

Wrong role calling a protected endpoint gets HTTP 403. No token (or a bad
token) gets HTTP 401. tenant_id always comes from the login token, so one
school can never read another school's data.

7. AUTHENTICATION AND SECURITY
--------------------------------------------------------------------------------
  - RS256 JWT (private key signs, public key verifies). Keys live in
    /etc/keys/*.pem and are mounted read-only into containers.
    Generate with:  sudo ./scripts/gen-keys.sh
  - Passwords hashed with bcrypt. Accounts can be disabled (403 on login).
  - Self-register is limited to driver/parent/teacher roles. Admin accounts
    are created by an existing admin (POST /auth/users, admin-only), except
    the very first user of a fresh tenant, who bootstraps as admin.
  - Refresh tokens are revocable: logout stores a hash in Redis and the
    refresh endpoint rejects revoked tokens.
  - Rate limits: login 10/min per IP, register 5/5min per IP (HTTP 429).
  - CORS defaults to "*" (ALLOWED_ORIGINS env) for demo simplicity.

8. DATA MODEL (key entities, per-tenant database)
--------------------------------------------------------------------------------
  users        id, email, password_hash, full_name, phone, roles[], is_active
  vehicles     id, plate_number, type, make/model, seating_capacity, status
               (deletes are soft: status='inactive')
  drivers      id, user link, license_no, experience, status
  routes       id, name, route_code, start/end points
  stops        id, route_id, name, landmark, latitude, longitude,
               stop_order, radius_meters (geofence)
  students     id, name, student_id, class/section, father/mother phones,
               route_id, pickup_stop_id
  trips        id, route_id, vehicle_id, trip_type (pickup/dropoff),
               scheduled start/end, status (scheduled/in_progress/completed)
  attendance   id, trip_id/date, student_id, status (present/absent)
  gps_points   vehicle_id, latitude, longitude, speed, heading, recorded_at
  geofence_zones id, name, stop link, radius_meters, polygon/circle
  alerts       id, type (e.g. geofence enter/exit), message, read flag

  /tenants    tenant info/provisioning
  /notifications, /analytics, /ridership, /fleet, /maintenance, /geo

11. INSTALLATION AND SETUP (in depth)
--------------------------------------------------------------------------------
PREREQUISITES
  - Docker + Docker Compose, Node.js 22, Python 3
  - Phone with the Expo Go app (for the mobile demo)
  - For the LAN-IP phone setup, laptop and phone on the same Wi-Fi

STEP 1 - Get the code
  git clone https://github.com/abhishek-mule/Busly.git
  cd Busly

STEP 2 - Backend keys (one time only; back up /etc/keys afterwards)
  sudo ./scripts/gen-keys.sh
  # creates /etc/keys/private.pem + public.pem (RS256 JWT signing)

STEP 3 - Start the backend (12 services + optional public tunnel)
  docker compose --profile tunnel up -d
  curl localhost:8000/health        # expect {"status":"ok",...}
  # Public URL (free, no account/card):
  docker compose logs cloudflared | grep trycloudflare
  # NOTE: the trycloudflare URL is random and changes whenever the tunnel
  # container is recreated. Re-check the logs after every `up`.

STEP 4 - Seed demo data (idempotent: only creates what is missing)
  python3 scripts/demo-seed.py
  # creates accounts, DEMO-01 bus, Demo Route + 3 stops, 2 linked students,
  # today's pickup + dropoff trips, and pushes a fresh GPS position.
  # Re-run every demo morning to refresh trips + live position.

STEP 5 - Admin dashboard
  cd admin
  npm install                        # once
  NEXT_PUBLIC_API_URL=http://localhost:8000/api/v1 npm run dev
  # open http://localhost:3000/login (dev mode reads the env var at startup;
  # NEXT_PUBLIC_* values are baked in at build time for production builds)

STEP 6 - Mobile app
  cd busly-app
  npm install                        # once
  # Same Wi-Fi as the laptop:
  EXPO_PUBLIC_API_URL=http://<laptop-LAN-IP>:8000/api/v1 npx expo start
  # Different network (phone on mobile data):
  EXPO_PUBLIC_API_URL=https://<tunnel-url>/api/v1 npx expo start --tunnel
  # Scan the QR code with Expo Go (Android) or the camera app (iPhone).
  # Find the LAN IP: Linux `hostname -I`, macOS `ipconfig getifaddr en0`,
  # Windows `ipconfig` (IPv4 under Wi-Fi). Use the 192.168.x.x address,
  # never 127.0.0.1. If the QR scan hangs, allow port 8081: sudo ufw allow 8081

STEP 7 - Verify the loop
  1. Admin login (admin@busly.com / admin123) shows real data.
  2. Driver login on phone, Start Trip -> Live badge.
  3. Parent login on phone, Tracking shows the bus on the map.

STOPPING / RESTARTING
  docker compose ps                  # what is running
  docker compose logs -f gateway     # follow logs (Ctrl+C to exit)
  docker compose down                # stop everything
  # After a reboot just run the `up -d` command again (restart policies
  # keep everything alive across normal restarts, not reboots).
  # After changing backend code: docker compose up -d --build <service>

12. HOW IT WORKS (key request flows)
--------------------------------------------------------------------------------
LOGIN
  App -> POST /api/v1/auth/login {email, password, tenant_id}
  Auth checks bcrypt hash -> returns access_token (short-lived RS256 JWT
  carrying user_id, tenant_id, roles) + refresh_token. Every later request
  sends `Authorization: Bearer <access_token>`; the gateway verifies the
  signature with the public key and enforces role scopes.

DRIVER TRIP + LIVE GPS
  Driver taps Start Trip -> POST /trips/{id}/start (status=in_progress).
  The phone's foreground location watcher POSTs /gps/location every ~10s
  with vehicle_id + coordinates. Geo service stores the point and checks
  geofence transitions against the route's stop zones (Redis keeps last
  inside/outside state) -> crossing the circle posts an enter/exit alert.

PARENT TRACKING
  Tracking screen loads linked children (students whose father/mother phone
  matches the parent's phone), their routes, the route's stops, the latest
  trip, and /gps/active positions. Map centers on stops + bus position,
  polls GPS every 8s. Pull-to-refresh reloads everything.

ATTENDANCE
  Driver (per trip) or teacher (roll-call) marks present/absent -> POST
  /attendance. Parent Children screen and admin attendance page read the
  per-day history.

ROUTE OPTIMIZATION
  Admin picks a route -> POST /routes/{id}/optimize enqueues a Celery job ->
  worker loads the route's stops, runs nearest-neighbor TSP, rewrites
  stop_order, posts a completion alert. Frontend polls job status.

REPORTS
  Report request -> Celery generates a real CSV into the shared report_files
  volume -> GET /reports/{id}/file downloads it (admin falls back to a
  live-generated CSV if the worker file is missing).

15. TROUBLESHOOTING
--------------------------------------------------------------------------------
  health check fails              -> docker compose up -d
  "Cannot reach the server"       -> app points at wrong API URL; check env var
  "Too many login attempts"       -> rate limiter (10/min/IP); wait 60s
  Admin lists empty               -> hard refresh the browser page
  Phone cannot reach Metro/API    -> same Wi-Fi + allow port 8081, or --tunnel
  Tunnel URL dead                 -> it rotated; re-read cloudflared logs
  429 errors                      -> rate limiter; wait a minute
  Dark map on phone               -> phone is in dark mode (maps follow theme)
  Login 401 everywhere            -> rebuild gateway+auth (key mismatch):
                                     docker compose up -d --build gateway auth-service

16. SCOPE NOTES (deliberately excluded from this zero-cost MVP)
--------------------------------------------------------------------------------
  No AI/LLM features. No push/SMS delivery (in-app alerts only). No online
  fee payments. No background GPS tracking (foreground only). The backend
  needs Docker and cannot run on Vercel (serverless); only the admin
  dashboard is Vercel-compatible (Root Directory = admin).
